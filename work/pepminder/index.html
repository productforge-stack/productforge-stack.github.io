PepMinder for Android

Shipping an Android app QA-first, with AI writing the code

I built PepMinder with Claude Code as the developer and myself as product owner and QA lead. Twenty years of testing experience decided how it was built: tests first, every change verified, and Android edge cases tried on emulators before users ever found them.

The problem with AI-written code

An AI coding assistant will write a feature quickly, and it will also say the feature works when it hasn't checked. On a reminder app that's a real risk: a missed or duplicate reminder means someone takes a dose at the wrong time.

So I treated Claude Code the way I'd treat a fast new developer on my QA team. I wrote the rules of engagement into the project's instruction file before any code existed, and held every session to them. The app has 417 commits from January to October 2026, released from v1.0 through v1.3.2.

What I owned

  • Product scope, features and release decisions
  • Test strategy, coverage targets and the definition of done
  • Regression planning, defect triage and sign-off
  • Hands-on testing on Android emulators and devices
  • CI/CD gates, store listing and launch

Rules I set for the AI, in my own words

  1. Tests come first.Write tests first, then code to pass them. No feature is complete without passing tests.Red, green, refactor for every feature: the failing test is written and run before the code.
  2. Coverage is a target, not an afterthought.Aim for 80%+ coverage.Unit tests for the dose math, schedules and inventory; widget tests for every interaction.
  3. Accessibility from day one.Plan for dark mode, large text, voice-over from the start.Not a pass at the end of the project.
  4. Nothing merges red.Only commit if: All tests pass, feature is fully functional, no pending TODOs.One feature per commit, so any regression points to a single change.
  5. Test on the real platform.Manual and scripted runs on Android emulators, not just on the desktop test runner.

Four layers of automated testing

The suite has 165 test files. Each layer catches a different kind of failure, and fast layers run on every change.

Unit tests

Flutter test, fake services, injectable clock

Dose and concentration math, schedule and interval calculations, database migrations, backup and restore, purchases, and notification scheduling, including runs pinned to a US time zone so daylight saving changes are tested every time.

Widget tests

flutter_test, shared test harness

Taps, forms, dialogs and navigation on every screen, plus a 338-case screen matrix that renders each screen at small widths and large text sizes with real fonts.

Golden tests

96 reference images

Pixel comparisons of key screens in light mode, dark mode, milligram units and large text. Any unintended visual change fails the build.

Integration tests on Android

integration_test, Android emulator

End-to-end flows from a fresh install: add a peptide, reconstitute it, schedule it, mark a dose taken and find it in the log; free-tier limits opening the paywall; backup and restore round trips; dark mode; and the setup wizard. 41 of 41 passed on the emulator at release sign-off.

How it ran

I split the work by risk. The most serious defects, missed or wrong reminders and data loss, were fixed first and test-first: a failing test that reproduced the bug, then the fix. I ran parallel AI agents on separate parts of the codebase, then reviewed and merged their work and checked that no test file had lost tests.

160 issues were logged and tracked by ID with the commit that fixed each one. A handful of low-priority items were deferred with my sign-off.

Four bugs the regression pass caught

Each one is the kind of bug that slips past a quick manual check. Each one now has a test that fails if it comes back.

Reminders shifted an hour after daylight saving

Every-few-days reminders added days to a local date-time, so after the March clock change an 8:00 AM reminder fired at 9:00 AM. A related bug made notification IDs collide just after midnight on the day after the change.

Caught by unit tests that run in a fixed US time zone across the March 8, 2026 change.

A failed restore could erase everything

Restoring a backup deleted the existing data first and had no transaction. One bad record partway through left the user with an empty app.

Caught by a test that restores a deliberately corrupted backup and checks the original data survives.

Deleted schedules kept reminding

Reminders were rebuilt before the schedule was deleted from the database, so a deleted schedule kept sending notifications. Archived items and snoozed reminders had similar gaps.

Caught by widget and scheduler tests that delete, pause and archive, then check what is still pending.

Android 14 scales large text differently

At 200% text on a small screen, a card was still clipped after it had passed the automated matrix. Android 14 and later scale large text non-linearly, so the fix based on font size was wrong. Labels like "Calculator" also broke mid-word.

Caught by hand on the Android emulator, then added to the screen matrix, which found one more.

Android-specific testing

Desktop test runners can't show how an app behaves on a real Android system, so I ran scripted passes on two emulator profiles: a medium phone on API 36 and a Pixel 6.

  • Reminders after a reboot, a time zone change and a daylight saving change, using clock jumps on the emulator
  • Notification actions (Taken, Snooze) with the app in the foreground and in the background
  • Upgrade from the previous Play Store version with existing data
  • 200% font scale on a 320 dp-wide screen, dark mode and TalkBack
  • Android manifest permissions checked by a unit test
  • Release-build checks before sign-off

Gates in CI

Every push to main builds an Android release in Codemagic. The build stops at the first gate that fails, so nothing reaches Google Play without passing all of them.

  1. Unit and widget tests
  2. Coverage of at least 93%
  3. Format check
  4. Signed app bundle
  5. Google Play internal track

Tests run with the time zone set to America/New_York, so daylight saving bugs show up in CI rather than in March. A date-arithmetic scan flags the risky pattern behind the DST bug if it appears anywhere new.

What this shows

AI can write most of the code. It can't decide what "working" means, which edge cases matter, or when a release is safe. That judgment is the QA job, and it's why PepMinder shipped with 4,334 tests instead of a list of known bugs.
