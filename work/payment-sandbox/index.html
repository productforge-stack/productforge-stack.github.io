A payment integration that never charges a card twice

For sixteen years I've watched payment integrations fail in the field, and the costliest failure is always the same: the network drops after the card is charged, the app retries, and the customer pays twice. I built this Kotlin library and Android app to show how an integration should handle it.

The rule that prevents double charges

When a request times out or the gateway returns a 5xx, the app doesn't know whether the card was charged. Treating that as "failed" and trying again is how customers get charged twice. Treating it as "approved" is how merchants lose money.

So every payment attempt gets an idempotency key before it's sent, and the library follows one rule:

  1. Look the payment up by its key
  2. Found: use that answer, don't resend
  3. Not found: resend with the same key
  4. Lookup fails: try again, up to three times
  5. Still unknown: stop and flag for reconciliation

It never retries with a new key to get unstuck. The HTTP client's own silent retries are switched off too, so every retry is a deliberate decision in one place.

The scenarios it survives

  • Timeout after charge. Finds the charge by key and shows it as approved. Charged once.
  • Gateway error before charge. Confirms the gateway never got it, resends with the same key. Charged once.
  • Device offline. Nothing left the device, so it says so and offers a retry.
  • Gateway down. Can't confirm either way, so it stops and shows the key to reconcile.
  • Decline. A normal answer, not an error. Refund and void stay disabled.
  • Refund larger than the sale. Rejected, nothing refunded.

How it's tested

The key tests check two things: what the user is told, and how many times the gateway was asked to charge. If that count isn't asserted, the double-charge risk isn't tested.

Recovery logic

JUnit, a scripted fake gateway

Each failure is scripted call by call: timeout then found, 503 then not found, a flaky connection during the lookup, a resend that times out too. The tests assert the exact sequence of submits and lookups.

HTTP layer

OkHttp MockWebServer

A real local HTTP server checks the headers, the JSON, and how every status code, timeout and dropped connection maps to "nothing sent", "rejected" or "unknown".

End to end, and from Java

Simulated gateway, JUnit from Java

The full stack runs against a simulated gateway for each scenario. A separate test calls the library from plain Java, because many payment integrations are written in Java.

Android UI on an emulator

Jetpack Compose UI tests, GitHub Actions, Pixel 6 API 34

Every push boots an Android emulator in CI and runs the app's UI tests: entering an amount, choosing a failure, and checking what the screen shows. App logic also has JVM unit tests and Android lint.

How I used Claude

This is my first Kotlin project. I came to it from C#, Dart and a proprietary POS language, and built it with Claude Code the same way I built PepMinder: I set the rules and the tests, Claude writes code to meet them, and nothing merges until CI is green.

The rules live in the repo's CLAUDE.md: money as whole cents, one idempotency key per payment, look up before resending, never lower the coverage gate.

I also wrote a Claude skill that reviews any payment integration, ours or a customer's, against the same checklist and lists the tests that are missing.

Written for customers too

Integration work is half code and half explaining it. The repo includes what I'd hand a customer:

  • An integration guide with the API, Kotlin and Java examples, and a go-live validation checklist
  • A troubleshooting table written as support answers: symptom, cause, how to confirm it, fix
  • A sandbox app a customer can run to see each failure and what correct handling looks like
